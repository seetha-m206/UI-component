# Reconstructed preview: JotForm Workflows — Workflow Builder

Source record: `Research-Library/04-Component-Library/jotform/jotform-workflows-workflow-builder.md` (JF10, 2026-10-05).

## Evidence priority

Reproduced faithfully from the source record's live testing session:

- The BUILD tab opens on a **"Start Point" modal** that will not proceed past "Next" without a trigger explicitly selected — enforced here by disabling the "Next" button until `selectedTrigger` is set, and visually confirmed via a selected-tile highlight + checkmark, matching the record's "Rules & Validation" entry.
- The five trigger options (Form, Schedule, Integrations, Email, Webhook) and the "NEW" badges on exactly Integrations/Email/Webhook — confirmed in the source, not guessed.
- The **Form trigger's two-part configuration**: picking an existing form from the account's own form list, then a "when" condition (e.g. "For every submission"), before the trigger step can be saved — the source record's own confirmed finding, reproduced as a "Confirm" button disabled until a form is chosen.
- The main canvas's **vertical flowchart/pipeline**: a "START POINT" node showing the configured trigger, a downward arrow, and an "+ Add Element Here" placeholder — reproduced with the confirmed node/arrow structure, and chaining supported for multiple elements (the source record flags this as untested-beyond-one-step in its own Second-Pass Flags, so this preview demonstrates chaining up to several steps as a reasonable extrapolation of the documented "chains a new step beneath the trigger node" action, not a claim that the real product's exact connector/branching behavior beyond that was observed).
- The **teal/dark-green BUILD/SETTINGS/PUBLISH mode-tab bar**, reproduced as a distinct accent from Form Builder's orange and Sign Builder's green mode bars per the source record's Technical Data section.

## Deliberate scope reductions

- **Only the Form trigger has a deeply interactive configuration step.** The source record explicitly flags that Schedule, Integrations, and Email/Webhook triggers were never opened or tested end-to-end — only Form was bound to a real form and condition. This preview reflects that gap honestly: picking any non-Form trigger and clicking "Next" moves straight to the canvas with a generic trigger label (e.g. "Schedule"), rather than inventing a plausible-looking configuration screen for triggers the source never observed.
- **The Workflow Elements list (Form, Email, Approval, Approve & Sign, Task, PDF, Sign Document, Team Approval, Webhook) is a fixed demo set, not every real action type deeply interactive.** The source record itself notes that no action step was actually added to the canvas during its pass — only the trigger/Start Point was configured live. Consistent with this project's established scope-reduction precedent (e.g. `jotform-input-table-field`'s "+add column" placeholder), each element here is addable as a labeled node on the pipeline, but no element's own downstream configuration screen (e.g. what "Approval" actually asks for) is reconstructed — that would require a second live pass the source record flags as not yet done.
- **No branching/conditional (If/Else) connectors.** The source record's Second-Pass Flags explicitly call out that branching behavior was not observed this pass ("A second pass should chain at least one action step to observe the canvas's branching/connector behavior"). This preview only supports a single linear chain of nodes, matching what was actually confirmed.
- **SETTINGS and PUBLISH tabs are shown as plain sub-nav placeholders**, not deeply interactive. The source record's own PUBLISH findings (Quick Share, Embed, Platforms, Assign Form, Email) were only partially explored ("only QUICK SHARE's immediate view was captured"), so this preview surfaces the sidebar item labels without reconstructing any of their individual panels.
- **The Podo AI chat panel, Boards auto-creation on open, and the "+ CREATE" chooser's 6-way starting pattern are out of scope for this component-level preview.** Those are separate, cross-product findings in the source record (behaviors of Boards/Apps/the dashboard chooser, not the Workflow Builder canvas itself) and are not reconstructed here.
- Following this codebase's established precedent (`jotform-app-shell-builder`, `jotform-input-table-field`): this component is **not** `value`/`onChange`-shaped, so the generic `ReconstructedPreviewPanel` harness doesn't auto-wire external state to it. All interaction (trigger selection, form/condition binding, element chaining, mode switching) is managed with fully internal `useState`, seeded only by the `initial*` props so fixtures can open the preview at different points in the flow (Start Point modal / a configured trigger / a canvas with chained steps).
