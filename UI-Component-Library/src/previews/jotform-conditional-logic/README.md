# Reconstructed preview: JotForm Conditions (field-level conditional logic)

Source record: `Research-Library/04-Component-Library/jotform/jotform-conditional-logic.md` (JF8, 2026-10-05).

## Evidence priority

Reproduced faithfully from the record's live-tested findings, in priority order:

1. **Instant, non-animated visibility snap.** The record's own `MutationObserver`/`getComputedStyle` inspection confirmed the target field's container flips `display: none → flex` in a single discrete mutation, with no transition/animation on `display`/`opacity`/`height`. This preview reproduces that literally: the target field's container is **always mounted** and only its inline `display` style is toggled — no conditional unmount/remount, no CSS transition, no fade/slide. This single implementation choice is also what gives stale-value persistence "for free" (see next point) rather than needing a separate cache.
2. **Stale-value persistence across hide → re-show.** Confirmed live: filling the target field, hiding it, then re-showing it left the previously-typed value intact. Because the container is kept mounted (point 1) and the `<input>`'s value lives in ordinary React state that is never cleared on hide, typing into the field while visible, hiding it, and showing it again reproduces this exactly — tested in `JotformConditionalLogic.test.tsx`.
3. **The IF/STATE/VALUE + DO/FIELD rule editor**, including the confirmed behavior that the VALUE picker becomes a dropdown auto-populated from the chosen field's own answer options when that field is a choice-type field (`draftField?.type === 'choice'` branch) — reproduced for the one field pair the record actually tested (a Single Choice Yes/No source field and a text target field).
4. **The silent-dependency-breakage finding, both halves:** (a) deleting the field referenced by a condition is unconditionally permitted (no warning), confirmed via the record's delete-time test; (b) afterward, the Conditions list shows the exact confirmed error string *"ERROR: One or more fields have been deleted which are required by this condition."* under a red "MISSING FIELD" badge, and the respondent-facing target field **fails open** — it reverts to permanently visible rather than defensively hiding. All three sub-behaviors are reproduced verbatim, including the exact error string.
5. **The STATE operator set** (Is Equal To / Is Not Equal To / Is Empty / Is Filled) and **DO action set** for Show/Hide Field (Hide / Show / Hide Multiple / Show Multiple) are reproduced as the full, confirmed enumerations from the record's Rules & Validation section.

## Deliberate scope reductions (documented per the task brief)

- **Only "Show/Hide Field" is an interactive action type.** The record enumerates all 9 condition/action types in the real "+ Add Condition" picker (Show/Hide Field, Update/Calculate Field, Enable/Require/Mask Field, Update Options, Update Product List, Skip to/Hide a Page, Change Thank You Page, Change Email Recipient, Run Workflow). This reconstruction renders all 9 as real, labeled, described menu items for structural fidelity — but only "Show/Hide Field" is clickable; the other 8 are genuine `disabled` buttons with a `title` pointing back to this note. The record itself only live-tested Show/Hide Field (Second-Pass Flags: "Update Options," "Update Product List," and "Run Workflow" were identified from their labels only; "Change Thank You Page" and multi-action chaining were not opened/tested), so inventing interactive behavior for the other 8 would mean guessing past the evidence.
- **The AI "Describe your conditions" box is present but inert.** The record confirms it exists and is visually prioritized above the manual picker, but flags it as "not tested end-to-end this pass." It's rendered here as a disabled input + disabled "Generate" button for structural fidelity, not wired to any logic.
- **No multi-IF-row AND/OR combinator.** The record confirms a second IF row can be added with a flat, whole-rule Any/All (OR/AND) toggle, but this reconstruction is scoped to the single-IF-row rule the record's own live test actually built (one source field, one operator, one value). Building a second, untested axis of the UI (multi-row combination) wasn't part of the requested scope and isn't reproduced.
- **No multi-action chaining off one DO block.** The record explicitly flags this as "identified in the UI but not actually built out and tested" (Second-Pass Flags) — correctly left out here too.
- **Fixed two-field setup, not a generic field palette.** The record's live test used one specific pair — a 2-option Single Choice "Do you visit our coffee shop?" and a text "What is your favorite drink?" — so this reconstruction hardcodes that same pair (`SOURCE_FIELD` / `TARGET_FIELD` in `JotformConditionalLogic.tsx`) rather than building a generic form-field editor the record never exercised.
- **"Delete field" is a demo-only control, not a real field-management UI.** The record's finding is about what happens to a *condition* after a field it depends on is deleted elsewhere in the builder (the BUILD canvas). Since this preview doesn't reconstruct the full BUILD canvas, the delete action is exposed directly on the rule card as a labeled demo button ("Delete field: ... (demo)"), plus a "Restore field (demo)" control so the broken state can be toggled back off for repeated testing — the restore control has no equivalent in the record (JotForm's real deletion is presumably permanent) and exists purely for this preview's demo ergonomics.
- **Whether a hidden field's value is excluded from the submitted payload is left unimplemented**, matching the record's own open question (Second-Pass Flags: "not independently confirmed for JotForm"). There is no Submit/payload simulation in this preview at all — it's scoped to the show/hide + stale-value + broken-rule behaviors the brief asked for.

## Uncontrolled/self-contained pattern

Following this codebase's established precedent (`jotform-input-table-field`, `typeform-choices-list-editor`): this component is not `value`/`onChange`-shaped, so the generic `ReconstructedPreviewPanel` harness doesn't auto-wire external state to it. All interaction — adding/editing/deleting rules, the respondent-preview toggle, the typed drink value, and the delete/restore-field demo controls — is managed with fully internal `useState`, seeded once from `initialRules` / `initialSourceFieldDeleted` props. This matches the task's "self-contained/uncontrolled" requirement directly.
