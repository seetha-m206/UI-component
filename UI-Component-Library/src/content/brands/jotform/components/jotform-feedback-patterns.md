## Location

Spans the whole product, not one screen: the My Workspace dashboard, the Form Builder (BUILD/SETTINGS tabs), Jotform Tables, and the live public submission form.

## Structure

JotForm's underlying feedback-component library is internally called "Magnet" — confirmed directly from markup, not inferred: the toast container's DOM id is `magnet-notification-container-id`, a confirmation dialog carries `data-magnet-dialog="true"`, and a tooltip wrapper is `class="magnet-tooltip-wrapper"` with a `data-tooltip-state="open|close"` attribute. FACT Underneath Magnet, specific libraries are visible: toasts render inside a `.Toastify` container (react-toastify or the vanilla Toastify.js), and the destructive confirmation modal is a genuine Headless UI `Dialog` (`id="headlessui-dialog-:rN:"`, `role="dialog"`, `aria-modal="true"`, `data-headlessui-state="open"`) styled with raw Tailwind utility classes (`bg-gray-900 bg-opacity-60 fixed inset-0 flex items-center justify-center`). FACT Notably, at least one tooltip in the builder ("Form Design," on an icon-only panel-toggle button) is NOT built on the shared `magnet-tooltip-wrapper` — it's a bespoke `<span class="panelToggle-tooltip ...">` with its own Tailwind classes, meaning there are at least two parallel tooltip implementations coexisting in the same screen. FACT

## Behavior & States

- Toast auto-dismiss timing: both observed toasts (field-delete and form-delete) disappeared on their own within roughly 3 seconds — confirmed tighter than an initial 5-second estimate by re-timing a second trial. OBSERVATION, timed across 3 trials, consistently gone by the 3s mark.
- "Destructive" deletes are soft-deletes with an undo window, at both the field level (Ctrl+Z) and the form level (30-day trash) — but the confirmation modal's own copy ("Are you sure you want to delete this item?") never mentions this safety net, so a user reading only the modal would reasonably believe the action is immediate and final. FACT for the soft-delete mechanism; INFERENCE for the "modal copy doesn't mention it" framing being a weakness.
- Confirmation modal presence is inconsistent by delete target: deleting an entire form (dashboard) gets a full confirm-dialog; deleting a single field inside that same form (builder) gets no dialog at all, just the undo-toast — the same severity-tiering pattern already confirmed in [[typeform-feedback-patterns]] (whole-form gets a rich modal, single-question gets nothing) and, more mildly, in [[destructive-confirm-modal-comparison]]'s own Zoho/Paperform/Google findings. FACT, directly confirmed for JotForm.
- Tooltip delay/positioning: tooltip appeared within roughly 1 second of hover (not instant, not noticeably slow) and was positioned adjacent to the trigger with a directional arrow, not centered or detached. OBSERVATION.
- A genuine toast-based error does NOT exist for public-form submission validation — JotForm uses a structurally different error surface instead, confirmed by direct DOM inspection. FACT, addendum 2026-10-06, directly resolves the Second-Pass Flag from the 2026-10-01 pass. The fixed-top red banner (`error-navigation-container`) is neither the `Toastify` container nor the `magnet-notification-container-id` system documented above for the dashboard/builder — both were confirmed absent on the public submission page via DOM query. This means JotForm runs at least two parallel error-communication systems: the Magnet/Toastify toast system (dashboard, builder — used for delete-undo confirmations, not errors) and a wholly separate, bespoke fixed-banner + inline-pill system (public form submission — used specifically for validation errors, both required-empty and format-invalid). FACT This is a materially different, and arguably better, answer than "JotForm doesn't use toasts for errors" — it has a dedicated, purpose-built, persistent (non-auto-dismissing) error UI for the one place errors matter most (a visitor trying to submit a public form), rather than a transient toast that could be missed.
- The error banner is reactive, not a static post-submit snapshot: its error count and grammar (singular/plural) update live as each field is corrected, without requiring another submit attempt. FACT, addendum 2026-10-06.
- Successful public-form submission also avoids toasts: it replaces the entire form with a full-page "Thank You" state, the same full-takeover pattern (not a transient notification) as the error banner's persistence — suggesting a consistent design choice for the public-facing form specifically: important outcomes (success or failure) get a persistent, hard-to-miss treatment, while toasts are reserved for the builder/dashboard's own lower-stakes, reversible actions (delete-undo). INFERENCE, drawn from the two confirmed facts above.

## Rules & Validation

- No rule found requiring typed confirmation (e.g., typing the form's name) before a destructive delete — a single click on "Delete Item" is sufficient. FACT
- The webhook-URL field's validation rule appears to require a well-formed URL with a host/TLD (a bare `http://not-a-valid-url` was rejected), but the exact rule (regex, TLD requirement, reachability check) could not be determined since no error text was ever shown. OBSERVATION

## Technical Data

- Toast container id: `magnet-notification-container-id`; CSS framework: `.Toastify` (Toastify.js / react-toastify family). FACT
- Confirmation dialog: Headless UI (`@headlessui/react` Dialog pattern), proper `role="dialog"` + `aria-modal="true"`, styled with Tailwind utility classes directly in the markup (confirms Tailwind is used in production, not just a build-time tool fully abstracted away). FACT
- Tooltip: two coexisting implementations — a shared `magnet-tooltip-wrapper` (state-driven via `data-tooltip-state`) and at least one bespoke `panelToggle-tooltip` span using inline Tailwind classes (`absolute`, `right-full`, `bg-gray-600`). FACT
- Dashboard loading state: skeleton/shimmer placeholders — gray rounded-rectangle bars mimicking the eventual row layout, plus a light-blue placeholder block standing in for the promo banner, shown while `workspace/` first loads. FACT, screenshotted mid-load.
- Builder loading state: a flat, solid pale-lavender background with no spinner, skeleton, or any visible loading indicator at all while the builder's JS bundle initializes — a user reloading the builder sees a blank colored screen for roughly a second with nothing to tell them it's working. FACT, screenshotted mid-load.
- Tables loading state: a near-instant transition through a plain blank white page before the grid paints in — no skeleton rows, no spinner observed in two separate loads, though the window was brief enough that a very short-lived spinner can't be fully ruled out. OBSERVATION, lower confidence than the other two loading states.
- Three different products inside one company show three different loading treatments (skeleton vs. nothing vs. a bare flash) — worth flagging as a cross-product consistency gap. INFERENCE from the three directly-observed facts above.
- Public-form error banner, DOM-confirmed (addendum 2026-10-06): `div.error-navigation-container` — `position: fixed`, `top: 0`, `z-index: 99999999`, `background-color: rgb(220, 38, 38)` — containing `div.error-navigation-inner` and a `button.error-navigation-next-button` (the "See Errors" control). Confirmed via query that this page has no `.Toastify` element and no `#magnet-notification-container-id` element — i.e., this is a genuinely separate, third feedback subsystem from the two (Toastify, Magnet) already documented above for the dashboard/builder. FACT

## Empty States

- Dashboard, zero forms: a full illustrated empty state — a drawing of three people at a desk with colorful app-tile icons, bold "You don't have anything here yet.", a one-line subhead "Create your first form to start collecting data.", and a prominent centered "+ CREATE" button. FACT, captured fresh after deleting the only form in the workspace.
- Tables, zero submissions: no illustration and no "nothing here yet" message at all — just a bare grid shell (header row + an "ADD" control for the first column, "Total 0" in the footer). This is a notably thinner empty-state treatment than the dashboard's, inside the same product family. FACT

## Competitor Comparisons

See [[destructive-confirm-modal-comparison]]'s own Competitor Comparisons table — now carrying JotForm's two cases (form delete, field delete) merged directly into its actual rows, not left as a separate draft. Narrative summary:

JotForm matches the severity-tiering pattern already confirmed across all four prior products: whole-form delete gets a full modal (Headless UI `Dialog`, proper ARIA), single-field delete gets only a toast-with-undo (Ctrl+Z). JotForm's whole-form modal is the first implementation in this comparison set confirmed to pair a **red destructive icon badge** with a **soft-delete-to-30-day-trash** safety net — a stronger combined pattern than Zoho's or Paperform's plain confirm-only modals, though it falls short of Typeform's richer itemized-consequences modal and Google's modal-plus-undo-toast combo. JotForm's field-delete case is the best-performing "no modal" tier of any product captured so far: unlike Typeform's and Zoho's equivalents (silent/no-undo), JotForm's gives an explicit undo-toast with a working Ctrl+Z shortcut — closer to Google's single-question-delete toast than to Typeform's complete silence. JotForm also introduces a new, previously-undocumented pattern across this library: a **third, fully separate error-feedback subsystem** (the public-form submission's fixed red banner) distinct from both its own Toastify and Magnet systems — no sibling product's Feedback record documents a comparably dedicated, persistent, live-reactive error surface for public-facing form validation specifically.

## Best Observed Approach

The soft-delete-with-undo-window pattern (Ctrl+Z toast for fields, 30-day trash + toast Undo for whole forms) is a genuinely good piece of this product: it de-risks the fast, modal-free field delete, and it means even the "full modal" form-delete path isn't actually a point of no return. The gap is purely in how that safety net is communicated — the confirmation modal's copy reads as final, and the field-delete toast's recovery path (Ctrl+Z specifically) disappears after ~3 seconds with no persistent "trash" affordance mentioned for fields the way there is for whole forms. RECOMMENDATION

The public-form submission error banner — persistent (non-auto-dismissing), live-reactive error count, a working "jump to first error" control, and per-rule-type inline messages (required vs. format) — is the single strongest validation-error UX confirmed across this library's five products for the specific case of a visitor submitting a public-facing form. RECOMMENDATION: no sibling product's own Feedback record documents an equivalently dedicated, persistent error surface for this exact scenario.

## Second-Pass Flags

- Whether JotForm uses a toast for any error at all (a failed third-party OAuth connection, a network-interrupted save) remains unconfirmed as a blanket claim — only the public-form-submission validation case is now settled as toast-free.
- Tables' loading state (blank white flash) should be re-checked with network throttling to get a longer, more reliably observable window.
- The "2 errors" banner's live-reactive recount was only tested going from 2→1 errors by fixing one field — not tested in the other direction (does the count go back up if a valid field is cleared again after being fixed?), and not tested with a format-rule field (email) counted alongside a required-rule field in the same multi-error state.
- The exact trigger/behavior of "See Errors" with more than one remaining error was not tested — does a second click jump to the next remaining error (consistent with the `-next-` in its class name), or always back to the first?
- The creation-flow chooser now also lists Table, Report, and Board as top-level "how would you like to start" options, in addition to the six captured in the P1 pass (Form, E-sign, App, Workflow, AI Agent, Website Widget) — worth a quick addendum to [[jotform]] §1.
