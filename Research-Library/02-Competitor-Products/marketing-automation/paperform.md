## 3. Features
- **Builder core — confirmed document/WYSIWYG paradigm:** the canvas is a real rich-text editor (Draft.js — see Section 8 for the DOM evidence), with questions embedded as atomic non-editable "card" blocks inside free-flowing prose, inserted via a Notion-style `/` slash-command menu or a left-gutter "+" toolbar. This is a **third builder paradigm** distinct from both already-documented competitors: Zoho Forms' scrollable all-fields canvas and Typeform's one-question-per-screen conversational flow. OBSERVATION, directly tested (typed prose between question cards, confirmed it renders as body copy).
- **Respondent-experience is a runtime toggle, not an authoring choice — the single most important structural finding this pass:** Theme & Appearance → "Form Experience: One-at-a-time vs. Classic form" lets one document source render as either a Typeform-style conversational flow or a Zoho-style scrolling page. OBSERVATION. **RECOMMENDATION (worth flagging for Section 15):** this unifies what Zoho and Typeform each built as a fixed, product-wide architectural choice into a single per-form setting — a genuinely different design approach worth comparing once each product's underlying respondent-rendering mechanism is captured at the component level.
- **AI-assisted creation:** a dedicated AI Create landing page (prompt text, voice input, and "Attach a PDF or image" to convert an existing paper form) that new accounts land on first. OBSERVATION, UI presence confirmed; generation itself not tested this pass (no destructive-action policy reason — simply out of scope for a first identification pass).

## 7. User Flows
- **Form creation:** AI Create prompt (or blank/template) → document-style builder, question cards inserted via `/` slash menu or "+" gutter toolbar → auto-save to draft ("SAVE DRAFT" → "SAVED DRAFT") → explicit Publish (a split button also offering Preview changes / Go to live form / Versions / Delete). - **Respondent experience — CONFIRMED, 2026-09-23 (see [[respondent-runtime-guided-vs-standard]]):** the Form Experience toggle genuinely produces two distinct respondent-facing runtimes from one Draft.js document, published and directly tested in both modes. Guided (One-at-a-time): a sliding window of ~3 mounted fields, auto/Enter-advance, a fixed top progress bar, no back-navigation control found. Standard (Classic): all fields mounted, normal scroll, single end Submit. Both render the document read-only (no `contenteditable`); the live page is served from an inlined `window._state`/`window._initialForm` payload with no separate API fetch. A real bug was found in the publish→new-draft handoff: immediately after a publish, the editor's "create new draft" call can carry stale pre-edit config and overwrite the just-published mode change (required re-toggling to stick).
- **Submission → results flow — CONFIRMED end-to-end, 2026-09-23 (see [[paperform-submissions-results-view]]):** a first attempt with representative data across every field type researched this pass was blocked by a hard product-level guard — Paperform will not accept any submission until the account owner's email address is verified (`POST .../submit` → HTTP 400). A same-day follow-up (PF9) verified the account owner's email, cleared the guard, and completed a real submission end-to-end: PDF-per-submission generation is now confirmed (the PF7 custom PDF template was genuinely rendered and stored, reachable via a signed S3 URL in both the submission detail view and the CSV export). Payment collection itself remains untested (no gateway connected, by design), but its *absence* is now a confirmed finding in its own right — the completed submission is labeled "Total Charged"/"Total Paid" throughout the owner-facing UI with no indication anywhere that no payment was actually taken, and product stock was genuinely allocated against it.

## 8. Technical Observations
> Only where directly observed this pass. Marked INFERENCE where not confirmed via DOM/network inspection.
- **Frontend tech clues — CONFIRMED via direct DOM inspection, deepened 2026-09-23 (see [[document-canvas-editor-shell]]):** the builder canvas is built on **Draft.js**. Root element `div.public-DraftEditor-content[contenteditable="true"]`; individual lines carry Draft block markers (`data-block="true"`, `data-offset-key`, classes such as `__unstyled paragraph block--empty block--focussed`). No Slate, ProseMirror, or Lexical markers were present. Question fields are genuine Draft `atomic` blocks (confirmed via the saved raw ContentState JSON, `"type":"atomic"` backed by an `IMMUTABLE` `fieldSection` entity), with each field's own title/help text stored as **nested Draft ContentStates** — "Draft inside Draft." This is a genuine, verifiable FACT about the product's editing technology, not an inference from visual behavior alone.
- **Backend/architecture inferences:** the draft-save model is a **full-document PUT**, not a diff/op-log — every save transmits the entire `convertToRaw` ContentState (~3.3 KB for a 4-block form) to `PUT /api/v1/form/<formId>/versions/<draftVersionId>`. CONFIRMED via network capture, 2026-09-23.
- **APIs/network behavior observed:** typing prose debounces to one PUT ~13–14s after the last keystroke. **Notably, inserting a question card or reordering one does NOT independently arm this save** — a card sat unsaved for ~50s after insertion (with the UI's own status label wrongly reading "SAVED DRAFT" the entire time) until a subsequent text edit triggered the debounced save. CONFIRMED, see [[document-canvas-editor-shell]] for the full trace.

- **Caching, uploads, real-time behavior:** NOT OBSERVED beyond the save-debounce behavior above.

## 10. AI Features
- **AI Create — now fully tested end-to-end via both entry paths (see [[paperform-ai-create]], 2026-09-23):** a dedicated landing page generating a form from a free-text prompt or an attached PDF/image. The text-prompt path is **conversational, not single-shot** — up to two rounds of AI-asked clarifying questions precede generation, and the resulting form was confirmed to use the exact option values supplied in those rounds (not generic filler). The image/PDF path skips clarification entirely and generates directly; tested against a real paper gym-membership form, it correctly captured all 7 fields with correct types (Date, Phone Number, Signature) plus added section headings, placeholder text, and required-field marking. Both paths took roughly 50 seconds and are **poll-based** (client checks every 2–3s), confirmed first-party-only (`paperform.co` + Paperform's own S3 for uploads), with no third-party AI vendor host observable. Generated forms land in the normal Draft.js builder via "Continue in the editor" — no separate AI-only editing surface. Two unpublished test forms were left in the workspace (`oksoip1n`, `lptflo7s`).
- **AI helper inside the Calculation Editor — fully tested end-to-end (see [[paperform-calculation-field-ai-helper]], 2026-09-23):** two real AI calls confirmed working (error-grounded "Fix", and free-text prompt-driven generation), both first-party-proxied through `paperform.co` with no third-party AI vendor host observable client-side. Iterative/multi-turn with client-held conversation history resent per call (server stateless per request); output is always a full-formula replace, gated behind an explicit "Apply"; every proposal carries a pre-computed Result value evaluated against sample data. The code pane itself is confirmed to be **another Draft.js editor** — the same editing technology already confirmed for the main document canvas.

## 12. Security & Permissions
> **CONFIRMED end-to-end, 2026-09-24 (PF13).** All three screens (SSO, Manage Team Members, Security & Password) live under Account Settings (`/account/…`), reached from the avatar menu. Observed on a Pro trial ($49/mo billed yearly) — Pro is **not** enough for any of the below; none of the three self-serve tiers shown in-app (Free/Pro/Business, up to $124/mo) lists SSO or team roles in their own feature bullet lists either, implying both sit behind a non-self-serve Enterprise/sales-contact tier not represented in the pricing table at all.

- **Single Sign-On (`/account/sso`) — fully gated, with zero provider information visible pre-upgrade.** The screen shows only "Configure Single Sign-On — Upgrade to configure SSO for your team," with no list of supported identity providers (no Google/Microsoft/SAML/OIDC names anywhere) — a total gate, not a preview-then-paywall pattern. The "Upgrade" link goes to Billing, not a dedicated SSO-upsell page, and Billing doesn't actually sell the feature it's gating. **Network:** the gate is enforced by a generic, parameterized `GET /api/v1/account/plan-for-feature?feature=sso` check, not a hardcoded page — the same call fires again on the Security & Password screen, which embeds a second, identical SSO card.
- **Manage Team Members (`/account/users`) — flat, single-role access on the current plan.** States outright: "Everyone on this plan has full access to every product and workspace, and can manage the team and billing. Upgrade to choose what each person can reach." No role picker anywhere — the one existing member shows a static, non-interactive "Owner" label; no Admin/Editor/Viewer distinction; no per-form/per-space scoping. **Architecturally distinct from the rest of the account settings app:** this screen loads a separate embedded micro-frontend (`platform-bsKvoAtq.css`/`platform-zVflBOrA.js`, served from a different CDN host, `duube1y6ojsji.cloudfront.net`, via `GET /platform/seats?embed=section`), plus its own data calls (`GET /api/v1/account/users`, `GET /api/v1/account/usage-limit-resolutions/Paperform/teams.seats`) — presumably shared infrastructure across Paperform/Papersign/Stepper's "unified workspaces."
- **Security & Password (`/account/password`) — four stacked cards.** (1) Change password — a single "New password" field, no current-password confirmation, no strength meter. (2) Two-factor authentication — explicitly off by default ("Two-factor authentication is not required on your account"), a "Require 2FA for all users" account-wide toggle, and **authenticator-app TOTP as the only second-factor method** (QR code + manual key at `/setup-2fa`) — no SMS, no email option anywhere in the flow. **No session-management UI at all** — no active-sessions list, no device list, no revoke/sign-out-everywhere control found anywhere in Account Settings. (3) A second, identical gated SSO card. (4) "Login with Google" — an ungated, individual OAuth login-linking option, ordinary personal convenience, not to be confused with the gated team-wide SSO above.
- **Bonus adjacent finding, relevant to PF7/PF12's S3-URL findings:** a "Paperform file storage access" card controls whether the team's uploaded files (form uploads, Custom PDFs, Signature-field images) are private-by-default (only accessible via a valid signed URL or by a team member) or switched to public via an "Enable public file access" toggle — confirming those signed URLs are signed *because* this account has never flipped that toggle.
- **Candidate "what we should learn" items:** (1) total pre-upgrade opacity on SSO — most competitors at least *name* their supported identity providers before gating configuration; Paperform shows nothing until upgrading or contacting sales; (2) permission granularity itself is a paid upsell, not listed as a plan-tier feature at any self-serve tier shown in-app; (3) anti-pattern — no session/device management UI anywhere, a security-conscious admin can't see or revoke active logins.

## 15. What We Should Learn
- **Patterns to adopt:** RECOMMENDATION — the single-document-source-with-a-respondent-rendering-toggle pattern (Form Experience: One-at-a-time vs. Classic) is worth studying further once the underlying mechanism is captured at the component level; it reframes what Zoho Forms and Typeform each treat as a fixed, whole-product architectural decision into a single per-form setting. **Also:** AI Create's conversational pre-generation clarification (asking up to two rounds of disambiguating questions before generating a form, confirmed in [[paperform-ai-create]] to produce results matching the clarified answers exactly) is a genuinely distinctive pattern neither Zia nor Typeform's Copilot uses — worth studying as a possible accuracy-over-speed tradeoff for AI form generation generally.
- **Patterns to avoid:** RECOMMENDATION — the confirmed **silent dependency breakage** in Question Visibility Logic ([[paperform-question-visibility-logic]]: editing or deleting a question that a rule depends on orphans the rule with no warning) and the confirmed **payment-status misrepresentation** ([[paperform-submissions-results-view]]'s PF9 update: a completed submission with no gateway connected is labeled "Total Charged"/"Total Paid" everywhere with no unpaid indicator) are both concrete anti-patterns worth explicitly avoiding in any similar system — silent failure modes around cross-references and financial state are higher-severity than the UI/accessibility defects also documented elsewhere in this product.
