## 6. UI/UX
- **Overall style / navigation model:** OBSERVATION — form builder is a three-pane layout: left field palette (categorized, scrollable), center canvas (live field arrangement), and a right-hand Properties panel that opens per-field on click. Form Settings uses a separate left sub-nav + right content-pane layout (see [[sidebar-settings-subnav]]).
- **Dashboard structure:** OBSERVATION, surveyed 2026-09-15 ("My Forms" dashboard). Three-zone layout: slim dark top bar (logo, Subscription link, device icon, AI/sparkle icon, notification bell — all undecoded), persistent dark left sidebar grouped under bold section labels (FORMS: My Forms/Shared Forms/Org Users' Forms; REPORTS: My Reports/Shared Reports; FOLDERS: My Folders/Shared Folders; MANAGE: My Tasks/My Approvals; SETUP: Users/Control Panel; standalone Trash at the bottom), and a light main content area with the forms list — a noticeably deeper, more CRM-style admin nav than anything inside the form builder itself. The "⋮" overflow menu expands to: Info, Duplicate, Enable/Disable, Move to Folder, Change Ownership, Change Form Type, Trash (styled red/destructive). Toolbar above the list: search icon, a sort-order toggle icon (confirmed to flip direction on click), and an "All Forms" filter dropdown (All Forms/Active Forms/Disabled Forms).

## 7. User Flows
- **Configure a binary settings toggle (e.g. Save & Resume):** Form Settings → Submissions & Storage → [sub-section] → click Enable/Disable radio → dependent options show/hide client-side → click page-level Save → single `PUT .../settings/{feature}` persists all pending changes for that section. OBSERVATION, fully mapped in [[toggle-radio-switch]]. Key finding: toggle state is **not** persisted until the separate Save action — local and server state are decoupled.
- **Add a field to a form:** click (not drag-required) any palette card → field appends live and interactive to the end of canvas, no config panel auto-opens → click the field's label separately to open its Properties panel. OBSERVATION, confirmed across Dropdown, Rating, File Upload, Yes/No.
- **Edit a Dropdown's choice list:** open field Properties → "Choices" → "Edit" → dedicated overlay with per-row +/− controls → all edits held in local/in-memory state, zero network calls, until the field's own Save/Done. OBSERVATION, fully mapped in [[choices-list-editor]]. Key finding: no drag-reorder; reordering requires the separate "Sort Choices" dropdown setting.
- **Publish / share a form:** OBSERVATION, fully traced (2026-09-15), with the toggle's persistence trace now **completed** (2026-09-18) — see [[publish-share-flow]]. Entry points: dashboard row's share icon, or the builder's left icon-rail "SHARE" item — both land on a dedicated Share screen replacing the builder canvas. The screen is laid out as a **three-level master-detail rail**: left column of sharing-method cards (Share With, Embed, Email Campaigns, UTM Tracking, Google Tag Manager & Custom Tracking) — the same card-list visual pattern as the dashboard's "New Form" chooser, confirmed reused across two unrelated flows — a middle sub-list that changes per card (for Share With: Public / Specific Users / Groups / All Users), and a right detail pane; Embed nests a second sub-list of its own (iframe / JavaScript / Hyperlink / Lightbox Pop-up / HTML & CSS / Website Builders). "Share With" → Public tab shows: the **Enabled/Disabled publish toggle** (the actual publish/unpublish control — see [[publish-toggle-switch]] for the toggle's DOM/JS, and [[publish-share-flow]] for its completed network trace), a click-to-copy Form Permalink field, a "Shorten URL" button backed by a real `POST /form/{name}/shorturl`, a server-rendered QR code with a genuine download endpoint (`/form/{name}/downloadcode?type=...`, not a client-side canvas trick), and social-share icon links. "Share With" → Specific Users tab offers private/internal sharing via email + a **two-line-option Permission dropdown** (Submit Form / Modify Form / Modify Form, Entries, Reports — each with a descriptive subtitle). The Embed tab offers 6 code-generation formats (iframe, JavaScript, Hyperlink, Lightbox Pop-up, HTML & CSS, Website Builders); embed code is built entirely client-side (string-templated from the already-loaded permalink), firing zero network calls when switching sub-options. A persistent "Access Form" button (top-right, every Share sub-screen) just opens the live public URL — it is **not** a separate publish trigger; the Enabled/Disabled toggle is the sole publish gate, and there is no separate "Publish" button anywhere in the flow — a form is enabled (live) from the moment it's created. **Key finding:** disabling public access requires confirming a modal warning (destructive, asymmetric friction; re-enabling does not); [[publish-toggle-switch]]'s original 2026-09-15 pass deliberately stopped before confirming this modal (to avoid leaving the test form disabled), so the actual persistence call was unconfirmed. [[publish-share-flow]] (2026-09-18) closes that gap on a throwaway form: the confirm click fires a real `PUT .../share/status {"enable_perma":false}` (200, empty body), and the confirm modal's "Yes" button is a solid-red fill rather than ghost/outline — the same solid-red pattern independently seen on the Trash-delete modal in [[destructive-confirm-modal-comparison]], flagged there for reconciliation as a possible product-wide (not single-instance) pattern. Disabled state renders an amber banner and desaturates/locks every Public and Embed panel control without removing it from the DOM.
- **View responses / dashboard navigation:** NOT OBSERVED at the response-analytics level (dashboard structure itself is covered in Section 6).
- **Switch Entries to Kanban view:** OBSERVATION, partially traced (2026-09-16), see [[entries-kanban-view]]. Entries screen's List/Kanban toggle → first use (or any use after a discard) requires a "Modify Kanban View" setup modal picking a choice-type field to group columns by, plus up to 4 card fields. View-switching itself is confirmed client-side (no network fetch), but the Kanban configuration is session-ephemeral — switching back to List View discards it with a confirmation warning. **Flagged incomplete:** the core card drag-and-drop-to-regroup interaction could not be verified — a substitute manual field edit confirmed the underlying data change hits `PUT /{account}/report/{reportName}/record/{recordId}`, but this was not confirmed as what the drag handler itself calls.
- **View Analytics dashboard (Form Metrics):** OBSERVATION, fully traced (2026-09-16), see [[analytics-dashboard-kpi-bar-map]]. Analytics/Reports → "Form Metrics" shows five KPI cards, a hand-built daily bar chart (a literal `<table>`, no charting library), and a "Form Views by Region" section combining a static world-map PNG with a data-driven region list. Selecting a different month/year fires a fresh `GET .../zfa/data/pageview?viewby=month&month_year=...` — server-side filtering, not a client-side re-slice, unlike the local-until-Save pattern seen elsewhere in this product. **Key finding:** the "map" is purely decorative (flat raster image, every region rendered identically regardless of actual traffic share) — all real regional data lives only in the adjacent progress-bar list, not in the map itself.
- **Edit a form's theme (full-screen "Create from Scratch" editor):** OBSERVATION, fully traced (2026-09-16), see [[theme-editor-split-pane-shell]]. Themes tab → "Create from Scratch" opens a full-viewport "Form Customization" modal: fixed 415px left config panel (icon tab strip + detail panel) beside a live preview pane that is, surprisingly, not a custom preview widget at all but a same-origin `<iframe>` rendering the actual form document. Changing a property (tested: Container Background → Gradient) writes CSS custom properties directly onto the iframe body's inline style from the parent document's JS — instant, no transition/animation, zero network calls. Everything is held client-side until the green Apply button; closing with unsaved changes triggers a confirmation dialog ("Changes are not applied to the form") and discards cleanly with no server trace. **Key finding:** confirms the same decoupled-local-state-until-explicit-Save pattern already seen in [[toggle-radio-switch]], now shown to extend to a much heavier full-screen editor, not just simple field-level toggles.

- **Frontend tech clues:** OBSERVATION — heavy reliance on jQuery (`.addClass`/`.removeClass`/`.show`/`.hide`/`.fadeIn`/`.fadeOut`) and inline `onclick`/`onchange` HTML attribute handlers throughout the builder and settings UI, rather than a modern reactive framework's event-binding pattern. ## 15. What We Should Learn
- **Patterns to adopt:** decoupling local UI state from server persistence via an explicit Save action (reduces accidental network chatter, seen consistently across toggle/field interactions) — though this trades off against user expectations of auto-save.
- **Patterns to avoid:** leaving dead/duplicate DOM trees in production (the 0×0 legacy sidebar) — creates real risk for anyone doing DOM-based automation or scraping against the app, and is a maintainability smell; wiring `aria-*` attributes without actually updating them (Rating field) — worse than omitting them, since it signals false accessibility support.
